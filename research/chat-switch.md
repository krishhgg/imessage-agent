# Switching chats on Messages 26

Scope: macOS 26.2, Messages 26.0 build 1450.300.41.1.4 (Mac Catalyst). This revises how research/messages-states.md switches chats. Where the two disagree, this document wins, and section 8 lists every state map item it changes. Evidence labels are the same as there: Measured, Reported, Code and Assumed. T is the target chat. E is the chat the user had selected. P1 to P7 here name this document's probes. They aren't the state map's guards P2, P3, P5 and P6.

## 1. Summary

A tapback or Undo Send has to find its bubble in T's transcript, so T has to be the selected chat. The bridge selects it by pressing T's row in the conversation list. On this Messages that press does nothing while Messages is hidden or minimized, which is the only state the bridge presses in today. So today a hidden tapback works only when T is already selected. For any other chat it ends in `wrong_chat` after the 2 s transcript wait, with nothing else pressed. It fails closed, but it doesn't work. PR #10 replaces that with section 4's refusal, with no press.

The proposal:
- **Act in place when T is already selected.** No switch, no hide, no unhide and nothing to restore. On a hidden Messages this is today's path, which worked in S3 under another app's grant (Measured). On an unhidden one it waits for the probe for that window state.
- **Switch with a selection driver** that presses, reads the selection and presses again until only T is selected. It presses only T, E, or a row the bridge itself just added to the selection. It handles both a press that toggles a row in a multi-selection, as Messages 26 does, and a press that selects a row alone.
- **Switch parked for a hidden Messages.** Move the window past every display while Messages is hidden, unhide it there, switch, act, switch back, hide it and move it back. The user sees nothing unless Messages comes to the front during the span. Then the window comes back on a display at once, and Messages either stays in front, when the input captured at the activation shows the user chose it, or hides again once focus is back on the earlier app. If the window can't be moved back, Messages hides again whatever the input showed, and the window moves back once Messages is hidden. This waits for probes P1, P2 and P7.
- **Switch in view** when the window is already on screen and Messages isn't frontmost. The user sees the chat change and change back. Row presses there don't raise or activate Messages (Measured). The bubble action there waits for probe P4.
- **Refuse everything else** with `busy: chat not open in Messages` and a fix line that leads to a state the bridge can act in. Until P4 passes, that is `fix: open <target> in Messages, hide it (⌘H), then retry`, because a hidden Messages with T selected is the one measured path. After P4 it is `fix: open <target> in Messages, then retry`.

Hiding Messages no longer helps with anything, since a hidden press does nothing. So the state map's "hide, act, unhide" and "hide, foreground, unhide" flows go away, and the bridge never hides a window that was on screen before the action. It hides only to undo its own unhide (steps 4 to 7, an activation that isn't a takeover, display changes, Mission Control and recovery).

Foreground edits and threaded replies keep today's hidden step 1, which now presses no row and goes ahead only when T is the selected row. So on Messages 26 they run only when T is already selected. Otherwise they return the same busy line, always with the ⌘H fix line. A parked switch for them is left for later.

## 3. The selection driver

The driver is a new call in Targeting.swift next to PR #10's `selectChat`, which presses nothing and stays as the no-press check (section 8). The driver is a loop that leaves exactly one row selected. The forward leg goes from E to T. The restore leg goes from T back to E.

**Starting point.** The leg starts only when exactly one row reads `AXSelected` and the transcript matches that row's chat (the state map's G2 and G3 capture). Between 2 and 6 s after the bridge's own hidden launch, one row read selected with its transcript loaded (section 2). That holds once the list has loaded. Before then the list's children are `AXGroup` placeholders, which `conversationRows()` skips, and PR #10 waits up to `listLoadTimeout` (6 s) for the list to load. States 1 and 8 don't switch (section 4), so they need no exception. Any start with no selected row refuses as state 26 or 33. A transcript with no selected row means the reader is missing the selection, for example a pinned chat shown as a tile.

**The opening press.** The row to open, T going forward and E in the restore, is found by its row description rebuilt from chat.db at that moment, with the lookalike rule (`ChatTargeter.hasLookalike` in Targeting.swift). It must match exactly one loaded row, or the leg stops before pressing. A row without Messages' English row actions isn't pressed, as PR #10's `selectChat` refuses it (`UINames.showsEnglishRowActions`). No index or element is reused from an earlier read, because rows move when messages arrive. The press runs the path's final check right before `AXPress`, with no AX read between them (BUILD-PLAN entry 50).

**After the press**, the driver reads the selection every 0.1 s for up to 1 s:
- Only the opened row selected: go to the transcript check below.
- The opened row and the earlier row selected: make the collapse press, then read again.
- No change through the whole 1 s poll: stop and don't press again. An unchanged first read doesn't end the wait. A slow press that lands later is caught by the final cleanup read below, if it lands before that read.
- Anything else, including a third row selected or an unknown `AXSelected` read (G14): stop.

**Done means the transcript matches.** One selected row isn't enough, because the selection can move to T while the transcript still shows E. The leg is done only when the opened row is the one selected row and the loaded bubbles match that chat's signature, waited for with `settleTimeout` (2 s, `ChatTargeter` in Targeting.swift). A mismatch stops the leg: going forward the result is `error: wrong chat`, and on the restore leg it adds G3's `chat not restored: an unknown chat is selected`. The bubble action runs only after the forward leg is done. A forward leg that stops for any reason, here, on a failed check or on overrun, skips the bubble action and goes to the exit order: the restore leg if a press was made, then the two-row check, then step 7 when parked. Section 4's hide-first exits and its takeover branch skip the first two.

**The collapse press** takes the earlier row out of the selection. That row is identified by `AXSelected` as the selected row that isn't the one just opened, and needs no text match. A press on a selected row only takes it out, so it can't open a third chat. On Messages 26 every switch is an opening press plus a collapse press. Where a press selects a row alone, there is no collapse press. A collapse press runs under the landing checks listed under "A final cleanup attempt for a two-row state" below. One that would show E also runs the unread check of "Read receipts".

**Read receipts.** The only rows pressed are T, E, and the selected row a collapse takes out. On a toggle list the press that shows E's transcript again is the restore leg's collapse press. Where a press selects a row alone, it is the restore leg's opening press. So the state map's G3 unread check, for incoming rows in E above the journaled highest ROWID, runs inside the final check of both. If E has new unread rows before the opening press, the restore leg doesn't start and T stays shown. If they arrive before the collapse press, the collapse goes the other way: it takes E out again and T stays shown. Either way the result adds `chat not restored: new messages in <E>`.

**A final cleanup attempt for a two-row state.** A stop, a failed check or an overrun can leave T and E both selected, with no transcript. Before any end hide and before the result, the bridge reads the selection once more. In switch parked, the hide-first exits and the takeover branch of section 4 make no such press. The hide-first exits read the selection only once Messages reads hidden, for the result's notes. The takeover branch reads it once the worker's call returns, for the result's notes and the G15 notice (section 4). Otherwise, if exactly T and E are selected, found as in this operation, it makes one collapse press toward E when the unread check allows it, otherwise toward T. Any other selection gets no press. That press is exempt from the time caps and runs under the landing checks only:
- Messages isn't frontmost and has the same pid
- it is unhidden. In a parked flow the window is still parked. In view, the pointer isn't over its window
- no mouse button is held
- no modifier key is held. The probes showed Control and Fn had no effect, but Shift wasn't tested, and a held Shift could extend the selection across rows
- in view, no mouse event since the gate, as G16 requires
- parked, no Dock overlay shows (section 4)
- parked, neither the stop flag nor the takeover flag is set (section 4)

If even that press can't run and the operation made a press, the result adds `chat not restored: two chats selected in Messages`. In view, the state map's G15 notice says no chat is open in Messages. A press that lands after this read isn't caught. The next request's starting point then sees two selected rows and refuses (section 8, Tests).

**Never on a frontmost Messages.** The driver never presses while Messages is frontmost (the state map's G5 and G6).

**Errors.** A path check that stops a press means that press wasn't made. If no press of the operation was made, the result says nothing was pressed, with no `may have marked read` note, and the approval stays valid for one retry (the state map's G13). If an earlier press was made, the result keeps the note and the approval is spent. Today `UIResults.axFailure` in Targeting.swift maps any error that isn't an `AXDriveError` to `not_loaded`, and `UIResults.mayHaveActed` counts it as a press that may have run, so it gets that note. A takeover in switch parked follows the same rule. An `aborted: user took over` after a row press keeps the note and spends the approval. A bubble press that ran or may have spends it too, and the result is the chat.db verification's result with the `user took over` note (section 4).

## 4. Where the switch runs

The bridge picks one flow from its state sample, in this order. Every flow first passes the state map's G9 (lock, display and console), its G13 approval rules and, for a frontmost Messages, its wait for front.

**Act in place.** T is already selected. Act in place makes no row press and has nothing to restore. As PR #10's `selectChat` does, it runs the bubble action or the foreground effect only once T is the one selected row and the loaded bubbles match T's signature within `settleTimeout`. A selected T whose transcript doesn't match returns `not_loaded`, with no press (PR #10). The bubble action runs on the window where it is, in these states:
- hidden with one window (state 7): today's path, Measured in S3 under another app's grant (section 2). State 9 keeps its refusal, because the transcript and bubble lookups read a single window (`singleWindow()` in AX.swift) and today's window rules refuse several
- unhidden, on screen, not frontmost (state 10): after P4, behind the state map's G16 gate and final check
- unhidden and minimized (state 11): after P5
- unhidden on another Space (state 12): after P6
- unhidden and outside every display (state 18): after P2

Until a window state's probe passes, that cell returns `busy: Messages is open` with `fix: open <target> in Messages, hide it (⌘H), then retry`. A frontmost Messages still needs the separate in-front opt-in (the state map's G5).

**Switch in view.** Messages is unhidden and not frontmost. Its one conversation window is on screen on the current Space and isn't minimized, full screen or in Split View, and Stage Manager is off. There is one active display until P4's first second-display leg passes. Until P4's fully covered leg passes, P1's cover reading must find part of the window uncovered. That reading tests a 40 x 40 grid of points over the window against the on-screen windows above it. A fully covered window refuses with `busy: chat not open in Messages` and its fix line. The driver runs on the visible window under G16: the mouse gate, the pointer check and the final check before each opening press. Then the action, under the same check. Then the restore leg. The user sees the transcript go blank, show T, go blank and show E. That takes about 2 s when the presses land at once. The caps are the same as parked, counted from the mouse gate's pass: 5 s for the forward leg and the action, then 2.5 s for the restore leg. If an opening press changes nothing through the whole 1 s poll, the leg stops and the result is `busy: chat not open in Messages` with its fix line. It keeps the `may have marked read` note, since a late press can still land. Waits for P4, which adds the bubble action to the row presses already measured.

**Switch parked.** Messages is hidden with exactly one Messages window at any layer that is on a Space (state 7, strictly, so state 9 refuses even with Settings open), and the bridge has seen this Messages pid unhidden or active at least once (section 8, WindowRules.swift). The window is on the current Space, read with `CGSCopySpacesForWindows`, the function BUILD-PLAN entry 51 looks up (section 8, MessagesApp.swift), so a hidden window on another Space refuses. Stage Manager is off, read three-valued, and there is one active display until P1's first second-display leg passes. Waits for P1, P2 and P7. Right after the bridge's own hidden launch (state 1) or relaunch (state 8), P1's launch leg failed: the first unhide put the window back at its saved frame, so the park didn't hold (section 2). So states 1 and 8 act in place when T is selected and otherwise refuse. So does state 7 until the bridge has seen that pid unhidden or active, because a login item can launch Messages hidden the same way and the bridge may not have been running when Messages launched. Steps:
1. **Checks on the hidden window.** Run G2 on it, including state 24's check for dialogs at any layer. G2's unread rule applies as for an unhidden start, because the unhide shows E: if E has unread incoming rows, refuse with `busy: unread messages in Messages`. The unread leg in section 6 can lift this. Resolve T, check that its row is found exactly once, and capture E (G3).
2. **Gate.** Run the mouse gate (the state map's G1). Read the window's frame through `AXPosition` and `AXSize`, and its CG bounds.
3. **Park.** Journal the `parked` record (section 5). Pick the parking point: 3000 points to the right of the largest right edge among the active displays, at the window's own y. Set `AXPosition` there with `setWindowPosition(_:finalCheck:)`. The final check confirms that Messages is hidden, has the same pid and isn't frontmost, with frontmost sampled last. Read the position back. If it didn't move there, or the AX frame or the CG bounds touch any display, move it back and refuse. From here on, "still parked" means both: the AX frame is at the parking point, and the CG bounds touch no display. If the two disagree, the window doesn't count as parked.
4. **Unhide.** The final check runs the gate's instant checks (buttons, modifiers, pointer), then G2's unread rule on E again, then confirms that Messages is hidden, not frontmost and has the same pid. Then unhide. Poll `isHidden` and the CG bounds of every Messages window in the on-screen CG list together every 1/64 s for up to 1 s. If any of them touch a display at any poll, the user can see the window: hide at once (the hide's final check is the same pid and not frontmost), move it back once hidden, and refuse with `busy: chat not open in Messages`.
5. **Check the unhidden window.** Messages isn't frontmost, the front app is the one recorded in step 2, `AXMinimized` reads false, the window is still parked, and no other Messages window is ordered in at bounds that touch a display. Otherwise refuse, as a hide-first exit (below). A Messages window on a display is handled as in step 4, and a frontmost Messages goes to the activation rules under "Watching the front app". When those checks pass, confirm that E is still the one selected row and that its transcript matches the signature captured in step 1. If not, refuse as a hide-first exit with `busy: chat not open in Messages` and nothing pressed. The result adds `selection changed when Messages was unhidden` and no `chat not restored` note, since the operation made no press, even when the unhide alone brought back T and E selected. On 2026-11-08 the first unhide after a launch brought back a saved two-row selection (section 2).
6. **Switch, act, switch back.** Run the forward leg, the action and the restore leg. The final check of each opening press and of the bubble press confirms that Messages is unhidden, still parked and has the same pid, that no Dock overlay shows (below), that no mouse button or modifier key is held, and that no Messages window in the on-screen CG list touches a display. It reads frontmost last, after the AX read for "still parked", and confirms Messages isn't frontmost. A Messages window on a display is handled as in step 4: hide at once, move back once hidden, and refuse. Collapse presses use the landing checks from section 3.
7. **Hide and move back.** The hide's final check confirms the same pid, that the AX frame and the CG bounds touch no display, and that Messages isn't frontmost. If Messages is frontmost, the activation rules under "Watching the front app" below decide. After either branch there, that is after any activation during the span, the observer has already moved the window back to the journaled origin when its move back worked, so step 7 only confirms that the position reads back there and deletes the `parked` record. It doesn't count that frame as moved by the user and adds no `Messages window moved` note. If the observer's tries ran out, the focus restore branch hides Messages, and once Messages reads hidden, step 7 runs its hidden path below, the move back with its own final check and read-back. With no activation, if the AX frame and the CG bounds both touch a display, the user or macOS moved the window: leave it, delete the record, add `Messages window moved` to the result and show the G15 notice. If they disagree, hide Messages with step 4's hide final check (same pid, not frontmost), move nothing, keep the record as recovery does (section 5) and add `Messages window off screen`. Otherwise, including a frame that moved but touches no display, hide and poll `isHidden` for up to 1 s. The move back, to the journaled origin, runs only once Messages reads hidden. Its final check confirms the same pid, Messages hidden and that the AX frame and the CG bounds touch no display. Read the position back, then delete the `parked` record. If the hide or the move back fails, the record stays, the result adds `Messages window off screen`, and recovery retries (section 5).

Every exit after step 3, refusals and AX errors included, runs three things in order, except that the hide-first exits and the takeover branch below skip the first two. First the restore leg, if the forward leg made a press, as the state map's G3 requires. That covers a refusal after the forward leg, such as a bubble that isn't loaded. If E is still the one selected row and its transcript shows, the restore leg makes no press and adds no note. Then the section 3 two-row check, which catches a late press that has landed by its read. Then step 7. The forward leg and the action must finish within 5 s of the unhide. On overrun the bridge skips the bubble press, as the state map's G1 skips the effect, and makes no new opening press except the restore leg's. The restore leg has its own 2.5 s, and collapse presses are never cut off.

**Hide-first exits.** A refusal in step 5, a Dock overlay, a display change, an activation that isn't a takeover, or a Messages window found on a display in step 6 is a hide-first exit. The bridge doesn't count on its hide to keep the restore leg and the two-row press from pressing, because `isHidden` can lag the hide and the landing checks would still pass on an unhidden, still-parked window. So it sets the stop flag, skips the restore leg and the two-row press, hides Messages with step 4's hide final check, polls `isHidden` until Messages reads hidden, then runs step 7's move back. If Messages doesn't read hidden within step 7's 1 s, step 7's failure path applies. After an activation, the hide waits for the focus restore. Step 7 then only confirms the read-back when the observer's move back worked, and runs its move back once Messages reads hidden when the tries ran out, as the activation rules below say. The bridge may read the selection once, after Messages reads hidden, for the result's notes. If the operation made a press, the result adds G3's `chat not restored: <target> is selected` when T is the one selected row, and `chat not restored: two chats selected in Messages` when that read finds both. If it made no press, it adds neither.

**Watching the front app.** For the whole parked span, an `NSWorkspace` activation observer on the main run loop, away from the AX worker (the request's connection thread), watches for Messages coming to the front, because the AX calls block and a check before each press could come seconds late. The span owns the `parked` record while it runs, so these notifications go to the span, not to recovery.

On every activation of Messages during the span, the observer does three things before it picks a branch:
- It captures the input reads the moment it receives the activation, before the move back and its retries: whether Command or a mouse button is down, the seconds since the last modifier change and the last mouse-up, and the seconds since the last key event and the last key-down. The branch choice uses these captured reads, not later ones.
- It sets the stop flag. Every final check and landing check reads it, so no new press starts after the activation.
- It moves the window back to the journaled origin, on a display, at once and without hiding it, under the same 0.25 s rule in both branches (P7). It does this on its own AX element for the window, without waiting for the worker's call to return. That element gets its own `AXUIElementSetMessagingTimeout` of 0.1 s, so a press stuck in `AXPress` can't stall the main run loop, and the display and activation callbacks with it, for the 2 s `messagingTimeout` that AX.swift sets as every element's default. The write runs in `moveWindowBack(to:finalCheck:)` in MessagesApp.swift, not through AX.swift's `setWindowPosition(_:finalCheck:)`, and its final check confirms that Messages has the journaled pid. Each try is one set, then a read of the window's CG bounds, which sends Messages no AX message. Each try runs from its own main run loop timer, never as a loop inside the notification callback, so the run loop turns between tries. The callback captures the reads, sets the flag, schedules the first try and returns. A try that times out, or whose CG bounds touch no display, schedules the next. There are at most two tries, so the last one ends about 0.2 s after the activation, inside the 0.25 s. P7 measures the delay. If the window still touches no display after the second try, the observer ignores the captured reads and always takes the focus restore branch, because nobody can be using an off-screen window. Step 7 then moves the window back once Messages reads hidden, and both checks below still run.

The focus restore wait and the hide run on a serial queue the span owns, not on the main thread and not on the worker, which may still be inside `AXPress`. `NSRunningApplication` refreshes `isHidden` and frontmost only as the main run loop turns (Reported, Apple's `NSRunningApplication` documentation), so a wait inside the notification callback would never see the earlier app come to the front. The worker's `isHidden` polls need the main run loop turning for the same reason, and the timer for each try keeps it free.

The reads come through the `InputMonitoring` protocol, injected into the observer. Live, it is IMForeground's `HIDInputMonitor`, the reader G1 already uses, over `.hidSystemState`, so IMUI gains no `CGEvent` use and needs no new permission (section 8). The time reads use `CGEventSource.secondsSinceLastEventType`. The key read takes `.keyDown` and `.keyUp`, the key-down read `.keyDown` alone, the modifier read `.flagsChanged`, and the mouse-up read `.leftMouseUp`, `.rightMouseUp` and `.otherMouseUp`. The down reads are the ones G1's mouse gate names: Command from `CGEventSource.flagsState(.hidSystemState)` and the buttons from `NSEvent.pressedMouseButtons`. The release read can't tell Command from the other modifier keys. Outside the bridge's windows (below), any modifier change in the 0.5 s before the activation counts as a Command release. Inside them, it counts only when it is newer than the last `.keyDown`. A ⌘Tab still passes when no key-down comes between the Command release and the capture, because its own Tab key-down comes while Command is held, before the release. A key-down in that gap is newer than the release, so inside the bridge's windows the ⌘Tab reads as no takeover and takes the focus restore branch, and P7 fails that run. Typing with capitals then counts only when the activation falls between a Shift change and the next key-down.

What counts as a takeover depends on when the activation comes. Within G4's 1 s front-app watch after the step 4 unhide, and while any press call the bridge makes is in flight or returned less than 0.5 s before the activation, only Command or a mouse button counts: down, or released in the 0.5 s before the activation, with a modifier change counted as a release only when it is newer than the last key-down (above). A recent key event alone doesn't, because the user may be typing in the front app (the state map's case A3) when the bridge's own unhide or press activates Messages. The driver and `HiddenActionFlow.perform` record each press call's start and return for this, and the observer reads them. Below, these two spans of time are the bridge's windows. Outside them, a key event under 0.5 s old at the activation also counts. Then:
- **Takeover branch.** The captured reads count as a takeover. The user chose Messages, through the app switcher, the Dock, or, outside the bridge's windows, a keyboard launcher such as Spotlight, Alfred or Raycast with Return, `open -a` or a Shortcut run from a key. This is the only place the observer sets the takeover flag. The window is already back on a display, since tries that ran out always take the focus restore branch (above). The bridge presses nothing more and shows the G15 notice naming the chat Messages shows. The chat.db verification still runs. If the bubble press ran or may have, because it ran before the activation or was inside `AXPress` at it, the result is the verification's result plus the `user took over` note. Only when the bubble press never started is the result `aborted: user took over` (PR #10's `AbortReason.userTookOver` in Results.swift). Section 3's approval rule applies, so a press that ran or may have spends the approval. Then step 7 confirms the read-back and deletes the `parked` record.
- **Focus restore branch.** The captured reads don't count as a takeover, as when another process activates Messages, or the move back's tries ran out (above), whatever the reads. Siri, and a Shortcut run without a key press, make no key event, so they land here too, and so does a keyboard launcher's Return inside the bridge's windows. Messages shows briefly and hides again. G4's focus restore reopens the recorded front app. Once the earlier app is frontmost, the bridge hides Messages with step 4's hide final check and runs step 7. When the move back put the window on a display, step 7 only confirms the read-back at the journaled origin and deletes the `parked` record. When the tries ran out, step 7 runs its move back once Messages reads hidden, with its own final check and read-back (step 7's hidden path). If the earlier app isn't frontmost within G4's focus restore wait (`focusRestoreWait`, 2 s, in Limits.swift), the bridge falls back to the takeover branch, with the window already on a display. After tries that ran out there is no such fallback. The bridge hides Messages anyway, with a final check of the same pid and the AX frame and the CG bounds touching no display, and no frontmost condition, then runs step 7's move back once Messages reads hidden. After tries that ran out, whether or not focus returned, if the move back fails, or the hide fails while Messages isn't frontmost, the record stays, the result adds `Messages window off screen`, and recovery retries (section 5). If the hide fails and Messages is still frontmost with the journaled pid, the bridge runs section 5's frontmost rule once before the span ends. It moves the window back without hiding it, with that rule's final check and a read-back, and shows the G15 notice. If that read-back confirms the journaled origin, the bridge deletes the record and the result adds no `Messages window off screen`. Otherwise the record stays, the result adds `Messages window off screen`, and recovery retries. If the move back succeeds, step 7 deletes the record and the result adds no `Messages window off screen`. When the move back worked, the user sees Messages' window on screen briefly, then hidden.

The remaining overlap is accepted. Outside the bridge's windows, another process that activates Messages while the user types in another app takes the takeover branch. Inside them, a Shift change in the 0.5 s before the activation that is newer than the last key-down still counts as a Command release, so a user typing capitals takes the takeover branch too when the bridge's own unhide or press activates Messages between a Shift change and the next key-down. In both cases the window is already on a display, so the keys land in a chat the user can see, and the two checks below still report typed text or a sent message.

In both branches, after the branch's last step, the bridge looks for keys that reached Messages. The checks cover both T and E, since only those two chats can be shown. Each chat's baseline is its composer value from its last transcript check. For that, the driver also reads the composer at each transcript check, and step 5 reads E's composer when it confirms E's transcript. Before step 5's read, E's baseline is the composer value G2 read in step 1. A chat with no baseline yet, which can only be T before its first transcript check passed, is compared with the empty value, so a draft T already held also reports, which errs toward a notice. Only the shown chat's composer can be read. The other chat's composer counts as possibly changed when a row press was in flight at the activation, or had returned before it with its change not yet read, since that press may have moved the selection after keys landed. Otherwise it counts as unchanged, because the window was off screen until the move back and no press started after it. When no single chat is shown, as in the two-row state, both composers count as possibly changed. The bridge also checks chat.db for an outgoing row in either chat since the unhide, other than the row this action wrote, which is the row its chat.db verification matches. For each chat whose composer changed or may have, the G15 notice says typed text may be in that composer, and the result adds `typed text may be in <chat>'s composer`. For each chat with such a row, the G15 notice says a message was sent in that chat, and the result adds `message sent in <chat> while Messages was parked`. The notice names the chat or chats with a change.

A row press or the bubble press already inside `AXPress` at the activation can still land. Neither branch makes the two-row press after it. The worker reads the selection once its call returns, for the result's notes and the G15 notice. P7's fifth run measures this in-flight case.

**Display changes.** A display reconfiguration during the span (G17) is a hide-first exit. It hides Messages at once, with step 4's hide final check (same pid, not frontmost). The bridge then runs step 7's move back and ends the span.

**Mission Control and App Exposé.** Either one, opened during the span, may show the parked window with T's transcript (Assumed). The final checks in steps 4 to 7 and the landing checks read the on-screen CG list for a Dock window above the normal layers. If one shows, the bridge presses nothing more and takes the hide-first exit. It hides Messages with step 4's hide final check and runs step 7's move back. P7's third run measures what the Dock lists then.

**Refuse.** Every other state where T isn't selected:
- minimized (11), on another Space (12) and outside every display (18)
- several windows (9), Split View (13), full screen (14) and Stage Manager (15)
- no reachable window (16 and 17), until the state map's probes 3 and 6 pass for 16 and probe 6 for 17
- a hidden window on another Space
- the user in a full-screen Space with Messages' window on a desktop Space (39)
- locked, display asleep or off the console (36 to 38)
- any switch flow whose probes haven't passed

The result is `busy: chat not open in Messages`, except where the state map already has a more specific busy line, such as `Messages is in Stage Manager`. The fix line depends on the probes that have passed, so that following it leads to a state the bridge acts in. Until P4, it is `fix: open <target> in Messages, hide it (⌘H), then retry`, which leaves Messages hidden with T selected (state 7), where act in place is measured. After P4, it is `fix: open <target> in Messages, then retry` for tapback and Undo Send, since act in place then covers a window left on screen behind the front app (state 10). ## 5. Restore and crash recovery

New item in the restore contract (state map section 5):

| Item | Recorded from | Restored by | Restorable |
| --- | --- | --- | --- |
| Window position while parked | `AXPosition` and `AXSize`, and CG bounds | `AXPosition` set back while hidden, or unhidden on any activation of Messages during the span or when Messages is frontmost in recovery, then read back | Assumed. P1, P3 and P7 |

The order becomes: the chat, then hide, then the window position, then the front app, then later the quit. After an activation of Messages during the span, the window position comes first. On the focus restore branch, the front app and then the hide follow it. The takeover branch restores neither (section 4). When the observer's move back runs out of tries, the focus restore branch restores the front app if it comes back within `focusRestoreWait`, then the hide, then the window position (section 4).

**The `parked` record** is its own file next to the journal, apart from the action's entry. It holds the Messages pid, the origin, the size and the parking point, as numbers only. It is written before the park and deleted only after a read-back confirms the move back. Finishing or pruning an action's entry leaves it alone.

**Recovery moves the window and never presses a row.** It runs only on a record that no live span owns: at bridge start, at the top of every UI request before the state sample, and on `com.apple.screenIsUnlocked`, on Messages' NSWorkspace activate and unhide notifications, and on a display reconfiguration. The notification triggers need a running bridge (section 8, Install and uninstall). `install.sh --uninstall` asks the running bridge to run the `parked` recovery before `launchctl bootout`, so removing the bridge mid-span doesn't strand the window. A record is owned while the span that wrote it runs, so the bridge's own parked unhide never triggers recovery. Recovery and spans run on the same UI queue, one at a time. On an unhide or activate trigger, recovery first waits up to state 22's 1 s for `isHidden` and frontmost to agree, then picks between the hide rule and the frontmost rule below. Each move and hide in recovery takes the same final checks as step 7, except that the frontmost rule's move confirms Messages is frontmost in place of hidden:
- If the AX frame and the CG bounds both touch a display, the user or macOS moved the window, or the span's observer moved it back on an activation (section 4). Recovery deletes the record and changes nothing. If the window moved but still touches no display, the rules below apply to it.
- If the AX frame and the CG bounds disagree, recovery moves nothing, keeps the record and `doctor` reports `Messages window off screen`.
- If Messages has the journaled pid, isn't frontmost and its AX frame and CG bounds touch no display, recovery hides it if it is unhidden, which shows the user nothing because the window is off screen. It moves the window back and leaves Messages hidden.
- If Messages is frontmost, the user is in it and sees no window. Recovery moves the window back without hiding it, and shows the G15 notice naming the chat Messages shows, since the crash may have left T or no chat selected.
- If the pid changed and the new window touches no display, recovery moves it to the journaled origin, with a final check of the new pid. P3 shows whether Messages keeps the parked frame across a relaunch.
- The chat stays as recovery finds it. `doctor` keeps its line that Messages may be hidden and showing another chat.

The state map's G12 drops its hidden G3 restore press, since a hidden press does nothing.

`doctor` checks the window's frame against the active displays in every case, journal or not, and reports `Messages window off screen`. Until P3 passes, the line says the fix is unmeasured and gives no steps. After P3, the fix line is `quit Messages and open it again` if a relaunch brings the window back on a display, otherwise the Window menu's Move & Resize commands if Messages has them (Assumed).

**Coordinates.** Every frame test uses the display rectangles from `CGDisplayBounds` over `CGGetActiveDisplayList`. They share their coordinate space with `AXPosition` and `kCGWindowBounds`: origin at the top left of the main display, y growing down. `NSScreen` frames use a flipped y axis and aren't used for these tests.

## 7. Options considered

**For a hidden Messages:**
- **(a) Park the window off screen (chosen, if P1, P2 and P7 pass).**
  - For: the user sees nothing change, and the front app doesn't change (Measured for `unhide()`).
  - Against: AppKit may pull a titled window back on screen when it is ordered in. Tiling tools that hide windows by moving them, AeroSpace among them, park windows in a display's bottom-right corner, reportedly because macOS keeps part of a window on a display when it is moved by a program (Reported, not checked here). If that holds, the clamp happens at the AX set, before any order-in. Step 3's read-back catches it and P1 measures it, but P1 may well fail for this reason. Section 2's occlusion reading predicts a second reason: a window past every display can't be seen, so its row presses may do nothing whatever the frame. A crash while parked leaves the window off screen until recovery runs. Mission Control opened during the span may show the window.
- **(b) Unhide only when the front app's windows cover Messages' frame.**
  - For: no frame change.
  - Against: where an unhidden window lands in the window order is unmeasured. Translucent toolbars and sidebars on macOS 26 show the change through the blur. A window the user moves during the span shows Messages.
  - Kept as the fallback if P1 shows the pull back and P1's cover reading shows that the window comes back fully covered and still takes row presses. Under the occlusion reading a fully covered window ignores presses as a hidden one does, so (b) would work only with part of the window showing, where the user sees it.
- **(c) Open in New Window, act there, close it.**
  - For: the main window's selection never changes.
  - Against: it unhid Messages with a new 1024 x 768 window in the one run (Measured), so the user would see the switch. The second window trips the several-windows refusal, and Messages may reopen it at the next launch.
  - Rejected.
- **(d) An `imessage://` or `sms:` URL through `open -g`.**
  - Against: S3 shows it unhides Messages. For a handle that doesn't match an existing chat's exact form it opens a new message. It can't name a group chat, and the restore would need a URL for the earlier chat.
  - Rejected.
- **(e) Arrow keys posted to Messages' pid.**
  - Against: it sends keys to an app that isn't frontmost, depends on which element has focus in the list, and is unmeasured on Catalyst.
  - Rejected.
- **(f) Show Messages briefly at its own frame behind the front app.**
  - For: the press is measured there.
  - Against: the user sees Messages appear, switch, switch back and disappear, for about 2 s each time.
  - Not in v1. If P1 fails, it is a question for the maintainer, as a separate opt-in like foreground mode.
- **(g) Refuse unless T is selected.**
  - For: safe, and true today with a better result line.
  - It is the fallback for every state the other flows don't cover. If P1 fails, it is what v1 ships for a hidden Messages. PR #10 implements it.

**For a Messages that isn't hidden:** hiding it to switch is useless now, so the choice is between switching in view and refusing. Switching in view is chosen for a window on screen. Every other unhidden state refuses unless T is selected.

**For foreground mode:** a parked switch in step 1 would need E kept across the runner's retake loop (`ForegroundRunner.execute`), a parked restore after the finish, and one on every early exit. Foreground mode is opt-in and its actions aren't the goal of this change, so it stays at "T already selected" for now.
