## Chat switch probes (state map probe 4 and more)

The bridge switches chats by pressing the target chat's row in the conversation list (`AXPress` on the `AXStaticText` row, `Targeting.selectChat`). Spike S3 recorded this as working with Messages hidden. On this Mac today (macOS 26.2, Messages 26.0 build 1450.300.41.1.4) it doesn't. Only two rows were pressed: the self chat (row 9, found by its last message) and the row the user had selected (row 6), to put it back. The other chats have unread messages, and a press could send read receipts. Modifier keys read clear (`CGEventSource.flagsState`) before each press, except where noted.

| Messages state | Press | Selection after | Transcript | Messages frontmost |
| --- | --- | --- | --- | --- |
| hidden | row 9 | unchanged, [6] | still row 6's chat | no |
| hidden | row 6 (self chat selected) | unchanged, [9] | still the self chat | no |
| minimized, then unhidden | rows 6 and 9 | unchanged, [9] | still the self chat | no |
| on screen behind the front app | row 9 | [6, 9] | no transcript | no |
| on screen behind the front app | row 9, then row 6 | [9] | the self chat, 12 bubbles | no |

- With Messages hidden or minimized the press returns success and changes nothing. The row's custom actions still run (the tapback actions are custom actions too, which is why the hidden heart is possible).
- With the window on screen, a press adds the row to a multi-selection or takes it out. No transcript shows while two rows are selected. Pressing the new row and then the old one leaves only the new one selected, and its transcript shows. Messages stayed behind the front app, and its window kept its place in the window order, so a row press doesn't raise or activate Messages (probe 4).
- `AXSelectedChildren` on the list and `AXSelected` on the rows aren't settable. The rows also offer `AXShowMenu` and the custom actions Pin, Mark as Unread, Hide Alerts, Open in New Window and Delete.
- Open in New Window on the self row while hidden opened a 1024 x 768 window for the chat and unhid Messages (not frontmost). The tester closed that window with its close button.
- The first visible press was made by mistake with Control and Fn held down by an earlier synthetic Control-Right Arrow (see below). The same press with the modifiers clear gave the same [6, 9] result, so the multi-selection isn't from the modifiers.
- What this means for the bridge: `selectChat` presses only while hidden, so on this Messages it can't switch chats. A tapback or Undo Send aimed at a chat that isn't already selected ends in `wrong_chat` after the transcript wait, with nothing else pressed. It fails closed, but it doesn't work. A chat that is already selected still works hidden.

## P1, launch leg (2026-11-08)

The chat switch design, research/chat-switch.md, is in PR #5 and isn't on this branch yet. Its terms used here: T is the chat an action targets. P1 parks the hidden Messages window past every display with `AXPosition`, unhides it there, and presses a conversation row to see whether the press switches chats while the user sees nothing. Its launch leg runs P1 right after the bridge's own hidden launch. States 1 (Messages not running) and 8 (Messages hidden with no window) are the rows of the state map, research/messages-states.md (also in PR #5), that start from a hidden launch.

P1 was run once on a Messages the tester launched hidden the way the bridge does. Messages had been quit by the user. The run pressed only the self chat's row and the user's own earlier row. Before each press on the user's row, chat.db showed no unread incoming messages in any chat but the self chat since the earlier probes. A sampler read the on-screen window list every 1/64 s for the whole run.

- 00:48:21, `open -g -j -b com.apple.MobileSMS`. About 2 s later AX listed one window, 1024 x 768 at (1208, 191), hidden and not on screen, with the self chat selected and its transcript loaded. That isn't the frame the window had before the quit. The window server put it on Space 1. The user was on another Space.
- The park: `AXPosition` set to (6440, 191), 3000 points past the right edge of the main display. It returned no error, and the AX position and the CG bounds both read back at the parking point.
- The unhide: `isHidden` read false after 0.06 s, and Messages stayed behind the front app. The window then had 660 x 667 at (840, 648), the frame it had before the quit (the same frame recorded after the unlock). So the first unhide after a hidden launch replaced the parked frame with the saved one. The window touched the main display's bounds but wasn't on screen, because it was on Space 1. P1 pressed nothing while parked.
- The hide took 0.02 s. The move back to (1208, 191) returned no error and read back.
- The fallback restore then unhid the window where it was, still on Space 1 while the user was on another Space. After a press on the user's row, and then two on the self row, the selection read the user's row and the self row together, with no transcript, each time. The selection wasn't read between the first unhide and the first press, so it isn't known whether the press on the user's row added that row or the unhide brought back a two-row selection Messages had saved.
- The sampler took 178 samples. No Messages window touched a display in any of them, and the owner of the frontmost window never changed. Messages never became active.
- At the end Messages was hidden with both rows selected, and its window was 660 x 667 at (1208, 191) on Space 1.

What this means for the design:
- The launch leg fails. After the bridge's own hidden launch, the first unhide puts the window at its saved frame, so a park made before that unhide doesn't hold. States 1 and 8 stay at act in place when T is selected, otherwise refuse, as research/chat-switch.md already says until this leg passes.
- A Messages window unhidden on a Space the user isn't on stayed out of the on-screen list for the whole run. The press results there are inconclusive, as above.
- The plain parked leg (Messages hidden after it was last shown, not freshly launched) is still unmeasured.

Follow-up at 00:51, to put the user's selection back. Messages was still hidden with both rows selected, its window on Space 1 and the user on another Space. The tester unhid Messages in place and pressed the self chat's row three times, 0.5 s apart, to take it out of the selection. Each press returned no error, and the selection still read both rows after each one. The window stayed out of the on-screen list (144 samples, none touching a display) and Messages never became active. The tester then hid Messages, moved its window back to (840, 648) and quit Messages, which the user had quit before the probe.

- The Space the user was on in both runs, id 8702, is a full-screen Split View Space on the main display (`CGSCopyManagedDisplaySpaces` type 4, read later that night). Messages' window was on the main display's desktop Space, id 1. So "another Space" here means the user was working in a full-screen app.
- A row press on an unhidden window on a Space the user isn't on does nothing, the same as on a hidden or minimized window. That matches the reading that Catalyst ignores presses in a scene the user can't see. A window parked outside every display may count the same way, which would fail P1's plain leg.
- So the two-row selection after the launch leg most likely came from the first unhide, which brought back the window state Messages had saved, frame and selection together. The press on the user's row in the fallback probably did nothing.
- Messages saved that selection at the quit, so the user will see both rows selected the next time Messages opens, until a chat is clicked.


## Conversation rows after a hidden launch (2026-11-08)

Two read-only runs at 00:55 and 01:29, each while the Mac had been idle for 3 minutes. Each launched Messages hidden with `open -g -j -b com.apple.MobileSMS`, read the conversation list's direct children through AX, and quit Messages. Nothing was pressed. The reads printed roles, counts and flags only, no names or text.

- Every child returned a Bool for `AXSelected` in every read, and exactly one read true. No read returned an error or a missing value.
- About 1 to 2 s after the launch, the list's 11 children were all `AXGroup`, with no `AXDescription` and 5 or 8 actions each. Five of them held one `AXStaticText` with a description, and six held an `AXGroup`. The list was still loading.
- About 6 s and 12 s after the launch, all 11 children were `AXStaticText` with a description and 11 actions each, as in the earlier on-screen dumps. The selected row was the same one as in the first read.
- The bridge's `conversationRows()` keeps only `AXStaticText` children, and its launch wait ends at the first hidden window plus the 1 s visibility poll. So the first UI action after the bridge's own launch can find no rows and return `not_loaded`. That fails closed. The bridge needs to wait for the list to load after a launch.

## Stuck modifier keys

The probe that left full screen posted Control-Right Arrow as key events with the Control and Fn flags set, at the HID level, and no modifier-change events. Afterwards the system read Control and Fn as held (`flagsState` 0x20a40000) until the tester posted modifier-change events for Control (59) and Fn (63) with no flags (0x20000000). A synthetic key with modifiers has to post the modifier key down and up as their own events, or post to the target process only.
