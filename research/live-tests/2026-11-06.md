## Eighth build installed (2026-11-07)

Build: the eighth release-test build, the seventh plus the window fix in PR 7, 1580 tests. Codesign passed and launchd bootstrapped the agent. Full Disk Access, Automation and Accessibility were all kept with no prompt (eight rebuilds for the first two, five for Accessibility).

`doctor --ui`: 8 checks, 1 failing: `fail allowlist: the Keychain hash can't be read fix: approve each chat again with imessage allow <who>`. The seventh build saved that hash when the maintainer chose Always allow for the self chat, and this build can't read it. No dialog appeared, because `readHash` turns Keychain dialogs off. The allowlist reads as untrusted, so every chat, the self chat included, asks again, and foreground mode reads as off. That is the designed fail-closed path.

Why: the access list does name the bridge by its designated requirement, but since macOS 10.12 the login keychain also checks the item's partition list, which the system sets when the item is created. A build signed with a Team ID gets a `teamid:` partition that later builds share. This self-signed certificate has no Team ID, so the partition is the creating build's code hash, and every rebuild or update loses the item. The PolicyStore comment that a re-signed bridge keeps access is wrong for self-signed builds.

Still to check with the maintainer: whether the next Always allow, which deletes the old item and adds a new one with dialogs on, raises a Keychain password prompt.

The bridge's real item, read without dialogs by a separate read-only tool that looked up only that item: its access list names `~/Applications/iMessage Agent.app` for decrypt, and its partition list holds one entry, `cdhash:39a9f25f…`, the seventh build's code hash. That confirms the cause.

### Keychain behavior after a rebuild, measured (2026-11-07)

To answer the question above without the maintainer, a throwaway test used its own item (service `io.github.krishhgg.kc-test.throwaway`) in the login keychain, with dialogs off for every call (`SecKeychainSetUserInteractionAllowed(false)`). Build 1 and build 2 were the same program signed with one throwaway self-signed certificate and the same identifier, so they share a designated requirement and differ in code hash. Build 3 was an ad-hoc signed program with another identifier. Build 1 made the item the way `writeHash` does: `SecAccessCreate` naming the calling program, then `SecItemAdd`.

| Step | Result |
| --- | --- |
| build 1 reads | ok |
| build 2 reads | -25293 (errSecAuthFailed), no dialog |
| build 2 reads the attributes | ok |
| build 2 changes the data (`SecItemUpdate`) | ok, no dialog |
| build 2 deletes the item, then adds its own | ok, no dialog |
| build 3 changes build 1's data | ok, no dialog. Build 1 can't read the item afterwards (-25293) |
| build 3 deletes build 1's item | ok, no dialog |
| `/usr/bin/security add-generic-password -T <build 1>` plants an item | builds 1, 2 and 3 all read -25293 |

The same steps in a keychain made with `security create-keychain` gave no partition list, and there build 2 read build 1's item.

What this means for the bridge:
- After an update, Always allow works with no Keychain prompt: `writeHash` deletes the old item and adds a new one, and both succeed.
- Every update still leaves the allowlist untrusted until the user approves again, because only the build that wrote the item can read it.
- Tampering fails closed. A program that changes the item's data, or plants one, leaves an item the bridge can't read, so the allowlist reads as untrusted (`hashUnreadable`). Deleting the item while policy.json exists reads `hashMissing`. Deleting both gives an empty allowlist. No test found a way to give the bridge a hash it can read without the user's login password. The PolicyStore comment that a program running as the user could plant an item before the bridge's first save is too pessimistic for the login keychain.
- A Developer ID build would get a `teamid:` partition shared by every build and keep the allowlist across updates. Self-signed builds can't.

The throwaway items were deleted afterwards.
