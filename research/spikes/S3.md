# S3: UI actions with Messages in the background

Status: partial. It ran from another app's process, which already had Accessibility, and covered fresh outgoing test messages only. A confirmation run from the bridge waits on its Accessibility grant. The remaining criteria (old, repeated-text, offscreen, multipart and incoming messages) moved to the release tests in DESIGN.md.

Date: 2026-11-06, 10:00 to 10:20 PST, macOS 26.2. Tools: `spikes/s3/*.swift`. Every action ran on test messages I sent to the user's own Apple ID. The tree dumps print UI labels and identifiers. Message text is printed only when it contains a test token (`S2 spike`, `s2-`, `s3-`); other text shows as a length. Conversation-list action names such as `Pin <name>` still carried contact names, a phone number and the Apple ID, so I replaced them with `Pin <contact>` and `you@example.com` in the committed dumps.

User requirement added during S3: Messages must not need to be on screen or frontmost. All tests below ran with Messages hidden (`visible false, frontmost false`), and the frontmost app (Grok Bot or ChatGPT) didn't change.

## Accessibility tree facts (Messages 26.2)

- The transcript is `AXGroup id=TranscriptCollectionView`. Each bubble is `AXGroup` or `AXButton` with `id=Sticker`. Its description reads `Your iMessage, <text>, <h:mm AM>`, or `<sender>, <text>, <time>` for incoming messages, and text bubbles contain `AXTextArea id=CKBalloonTextView`.
- Bubble actions are named: `Heart`, `Thumbs up`, `Thumbs down`, `Ha ha!`, `Exclamation mark`, `Question mark`, the user's recent emoji, `Add Emoji as Tapback`, `Tapback Details…`, `Reply…`, `Attach Sticker…`, `Forward…`, `Copy`, `Delete…`, `Show Times`. Fresh outgoing messages also get `Edit` (15 min) and `Undo Send` (2 min).
- The composer is `AXGroup id=MessageEntryView` with `AXTextField id=messageBodyField`. It has buttons "add", "Record audio" and "Emoji picker", and no send button.
- Conversation-list rows are `AXStaticText` with description `<name>, <last text>, <time>`, plus actions `Pin`, `Mark as Unread` or `Mark as Read`, `Hide Alerts`, `Open in New Window` and `Delete…`.
- Menu items `Send Message`, `Reply to Message…`, `Tapback Message…` and `Edit Last Message…` are all disabled while Messages is hidden.

## Foreground opt-in tests (user chose "opt-in, off by default")

`spikes/s3/fg.swift` brings Messages forward only for the action. It hides Messages again and reopens the previous app afterwards. It refuses to run if the user pressed a key or clicked in the last 2 s, read with `CGEventSource.secondsSinceLastEventType(.combinedSessionState)` for keyDown and leftMouseDown only.

| Test | Result |
| --- | --- |
| `NSRunningApplication.activate()` from a background process | Refused. Cooperative activation on macOS 14+ kept the user's app in front |
| Setting `AXFrontmost` | Refused, same reason |
| `NSWorkspace.openApplication(activates: true)` | Refused |
| `/usr/bin/open -b com.apple.MobileSMS` | Works: Messages in front in about 450 ms. `open -b <previous app>` restores focus |
| Bubble `Reply…` action, then type and Return (foreground) | Sends, but as a plain message. Reply mode never engaged (rows 1110022 to 1110024) |
| Menu Edit > `Reply to Last Message…`, then set composer text and post Return | **Threaded reply works** (row 1110025 has thread_originator_guid). It targets the chat's newest incoming message, which in the self-chat was a 2024 note. With a bubble selected, the item reads `Reply to Message…`, but selecting a bubble through AXPress did not work |
| After the threaded reply, Messages stayed in the thread view, even after a row press or an `imessage://` URL | The next action has to leave the thread view first (Escape in the foreground) |
| Edit in the foreground: Escape, bubble `Edit` action, set the inline field, post Return | **Works** (row 1110026: date_edited set, body now holds the new text). The idle guard aborted the first tries while the user was typing, and the retry ran on the ninth try |
| Time away from the user's app | 1.4 to 2.2 s for reply, 3.3 s for edit (it includes the Escape and up to 2 s waiting for the bubble) |

## Hidden window lifecycle (S3b)

Tools: `spikes/s3b/` (vis.swift, winctl.swift, nsopen2.swift). `vis` samples every 10 ms with `CGWindowListCopyWindowInfo` for on-screen Messages windows at layer 0 taller than 100 px (owner pid and size only, no titles) and logs every frontmost-app change. Run from another app's process at 10:38 to 10:41.

| Case | Method | On screen | Result |
| --- | --- | --- | --- |
| Messages not running | `open -g -j -b com.apple.MobileSMS` | Never, in 1 run | Hidden, 1 AX window with transcript and composer, focus unchanged |
| Messages not running | NSWorkspace `openApplication`, `activates = false`, `hides = true` | Never, in 1 run | Same |
| Messages not running | Apple Event cold start (`count accounts`) | Never | Same, in this one run. The bridge still launches hidden first and doesn't rely on it |
| Hidden, window open | AXPress the window's close button | n/a | Works while hidden. 0 windows left |
| Hidden, no window | Press Window > `Messages` through AX (enabled while hidden) | Shown in 3 of 4 runs, about 1.5 s, behind the front app | **Unreliable.** It unhid Messages every time after the first run |
| Hidden or unhidden, no window | Quit through Apple Events, wait for exit, then `open -g -j -b` | Never, in 3 of 3 runs | **Works.** 1 window with transcript and composer, hidden, focus unchanged. Takes about 2 s |
| Unhidden, no window | `NSRunningApplication.hide()` | n/a | Returns false but takes effect within 250 ms. Poll `isHidden`, don't trust the return value |
| Messages not running, screen locked | File send through the bridge (cold start) | Never | Row 1110037 sent and delivered, transfer_state 5. Messages came up hidden with 1 window |
| Hidden, screen locked | Text send through the bridge | Never | Row 1110038 sent and delivered in 33 ms |

Frontmost-app changes that happened during these runs (Slack and Grok Bot) were the user's own switching. None lined up with a test action.

## Verdict

With Messages hidden, Heart add and remove and Undo Send worked, and the other bubble actions exist by name. Threaded reply and edit need Messages in front, so they sit behind an opt-in foreground mode that is off by default. In that mode, edit worked once, and reply worked once on the chat's newest incoming message. What ships in v1 is decided by the capability table and release tests in DESIGN.md section 4, not by this report.

## Not covered

- Older messages that are not loaded in the transcript. `AXScrollToVisible` and `AXScrollUpByPage` exist but were not tried.
- Incoming messages from other people, and group chats.
- Multipart messages (`p:1/`).
- The locked screen.
- Recreating a window when Messages has none is covered by S3b: quit and relaunch hidden. That costs about 2 s and is only done when no window exists and the send queue is idle.
- Running from the bridge process itself, which needs its own Accessibility grant.
