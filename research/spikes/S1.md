# S1: TCC attribution and grant survival

Status: pass, except the full-screen case of the panel, which the user did not confirm.

Spike code: `spikes/s1/` (Bridge.swift, build.sh, spike client, watch-grants.sh).
Setup: macOS 26.2 (Darwin 25.2.0), arm64. Bridge at `~/Applications/iMessage Agent Spike.app`, bundle id `local.imessageagent.spike`, LaunchAgent `local.imessageagent.spike` with a `Sockets` entry, `AssociatedBundleIdentifiers`, `LimitLoadToSessionType Aqua`.

## Results

| Check | Result | Evidence |
| --- | --- | --- |
| Self-signed cert can sign without being trusted | Pass. codesign finds the identity once the dedicated keychain is in the user search list. No trust-settings change needed. `find-identity` still shows CSSMERR_TP_NOT_TRUSTED. | build.sh adds and removes the keychain around codesign |
| Designated requirement | `identifier "local.imessageagent.spike" and certificate root = H"<spike certificate SHA-1>"`. It doesn't include the cdhash, so a rebuild signed with the same cert should keep the same DR. | `codesign -d -r-` |
| Hardened runtime | flags=0x10000(runtime), one entitlement: `com.apple.security.automation.apple-events` | `codesign -dvvv` |
| Socket activation | Pass. `launch_activate_socket("Listener")` returns the fd and the first `nc -U` connection starts the job | `spike ping` → `pong S1-BUILD-1` |
| Responsible process | Pass. The launchd-started bridge is its own responsible process (responsible pid = own pid, ppid 1), even though the client `nc` runs under another app that has its own grants | `spike whoami` |
| No inherited FDA | Pass. The app that ran `nc` has FDA, but the bridge gets `open()` errno 1 (EPERM) and sqlite3_open_v2 rc 23 (SQLITE_AUTH) on chat.db | `spike status` before grant |
| TCC auto-registration | macOS added rows for the bridge on first access attempt: `kTCCServiceSystemPolicyAllFiles` and `kTCCServiceAccessibility`, both auth_value 0. The app shows up in both Settings lists already, so the user only flips a toggle (no "+" picker). | system and user TCC.db, rows for this client only |
| FDA grant reaches the running bridge | Pass. TCC row set at 09:35:51 and the same bridge process (pid 4520) opened chat.db 2 s later with no restart. `launchctl kickstart -k` is not needed, but setup can keep it as a fallback | watch-fda.log |
| Automation prompt names the bridge | Pass. The user's TCC.db has `kTCCServiceAppleEvents` for client `local.imessageagent.spike`, target `com.apple.MobileSMS`, auth 2. `AEDeterminePermissionToAutomateTarget` returns 0 and a read-only script counts 6 accounts | `spike ae`, `spike ae-script` |
| Grants survive an update | Pass. S1-BUILD-2 changed the code (S2 ops added) and the cdhash (5efc4b0f to bab7ab57), with the same certificate and DR. FDA and Automation both still work and the TCC rows were not rewritten | build.sh S1-BUILD-2, then status, ae, ae-script |
| Grants survive a second update | Pass. S1-BUILD-3 (10:25, a test-only tapback op added) opened chat.db and ran the Automation script with no new grant | build.sh S1-BUILD-3, then status, ae-script |
| Finder launch hands off | Pass. With the job running, `open` leaves the launchd instance as the only one. With the job stopped, `open` starts an instance that kickstarts the job and exits, leaving one launchd-owned process with both grants | pgrep count 1 in both cases |
| Approval panel | Pass on the current Space: a `.statusBar` level, non-activating panel with `canJoinAllSpaces` and `fullScreenAuxiliary` was on screen and the user clicked "Allow once" (the button enabled after 1 s). Whether it shows over a full-screen app was not confirmed | `spike panel` returned `panel=allow` |
| Grants under any other app | Pass. The bridge is the only client with Automation for Messages, and no other client got a grant from these tests | TCC.db rows for MobileSMS |

## Verdict

The bridge design works on macOS 26.2. Permissions belong to the bridge, not to the app whose shell calls it, so Grok Bot's shell can drive Messages through it without the -1743 error that osascript gets. A self-signed certificate keeps grants across updates without touching trust settings. Setup needs two user actions (one FDA toggle, one Allow click), and macOS lists the bridge in Settings by itself.
